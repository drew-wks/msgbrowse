# Development instructions for this fork

- Read [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) before architecture, ingestion, storage, or media changes. Treat its project objective and retention requirements as authoritative; keep its implementation status and decisions current.
- Preserve implemented append-only iMessage retention. Never let source deletion, export refresh, or provider controls delete archived messages or attachment bytes.
- For explicit owner-directed exclusions, record removed Apple GUIDs and hashes in `imessage_excluded_messages` before deleting archived rows; preserve that ledger across backups and reimports. Exporter TXT does not carry Apple's Unknown Senders classification. Do not infer it from Contacts or treat every nonzero `chat.is_filtered` value as Unknown Senders.
- When `imessage_exclude_apple_filters` is enabled, import paired TXT/HTML with the matching read-only Apple database. Only owner-verified filter values may auto-exclude new GUIDs; ledger those GUIDs before ingestion. Hold unreviewed nonzero values, preserve existing archived rows, and never infer categories when the old source lacks filter metadata.
- `imessage_excluded_apple_senders` matches exact source phone handles by GUID, independent of exporter contact names. Keep owner-specific numbers in the private config, not the example config. Preserve GUID, hash, and noncolliding TXT fingerprint guards for any archived rows Drew explicitly removes.
- For owner-reviewed orphan cleanup, preserve the `content-v1:` ledger fingerprints used by TXT-only imports; check for collisions with retained messages before adding them. They cover parsed message time and body across renamed exports, but only paired Apple GUIDs provide a full identity guarantee when source text or times change.
- For owner-directed transactional cleanup, classify locally and conservatively. Protect substantive two-way conversations, groups, the owner's named keep list, and person-shaped sender labels, even when a message resembles a reminder or code. A name-like label is a reason to defer deletion, not proof of identity. Never infer spam solely from a numeric sender or lack of a contact. Record exact hashes for every source and Apple GUID plus noncolliding `content-v1:` fingerprints for iMessage before deleting rows. Schema v29's insertion guard must remain effective for every importer. A new transactional message not previously recorded in the ledger still needs a fresh classification pass.
- For owner opt-out exclusions, match only outgoing, whole-message `stop` or `quit` (case-insensitive). An `orphaned` export file combines unrelated messages and must never be excluded as a whole thread. Keep known blocked conversation names in exact import rules so later exports without the opt-out reply remain blocked.
- Reassign orphaned messages only from a read-only Apple database's unique GUID-to-chat link and a nonconflicting archive destination. Preserve message IDs and child media/link/reaction references. For metadata-only moves, use a consistent SQLite checkpoint and checked before/after comparison; reserve full media backups for media-changing work or archive milestones. A sender/contact name alone never proves the original chat.
- When auditing multiple Apple snapshots, reject conflicting GUID-to-chat destinations rather than choosing a source by date or sender name.
- Treat `imessage-exporter` as an external dependency. Keep ingestion compatible with its documented TXT and copied-attachment format; review exporter version changes before changing parsing or export invocation.
- Historical reconstruction pairs exporter 5.0.1 TXT and HTML from the same immutable source snapshot. Preserve Apple GUID identity across renamed conversations and append media found in later snapshots; fail closed when pairing is incomplete. Keep each backup's staging distinct and private.
- Legacy iPhone `msg_pieces` MMS uses the import-only `legacy_mms` source. Resolve outgoing recipients from verified `group_member` data, keep overlapping snapshot identities stable, and retain every accepted payload under archive-controlled media. Recover owner-eligible material with uncertain contact or direction only under `legacy_mms_review`, without asserting a contact or direction. Put materially different old SMS texts under `legacy_sms_review`; hold close Apple text variants for representation review. These review sources are import-only and their messages must survive missing source snapshots. `legacy_mms_review` media resolves from permanent iMessage storage. Never create a third visible message when source media can be attached to an identified Apple row instead.
- Retained `.ichat` records with verified Drew account identity but unresolved historical chats live in the synthetic `iChat review (unassigned)` iMessage conversation. Keep their Apple GUIDs intact so later exports cannot make duplicate message cards; use a checked GUID-to-chat move before assigning a real conversation. The review import records five- and six-digit sender GUIDs in the exclusion ledger, retains decoded embedded images under permanent iMessage media, and records other file-transfer GUIDs without claiming unavailable bytes. Do not infer Apple Unknown Senders classification from `.ichat` rosters.
- Nexus recovery uses the import-only `nexus_recovery` source for owner-eligible old observations without an Apple metadata match. Nexus has no Apple GUID; matches on handle, displayed second, direction, and body are possible duplicates, never proof of shared identity. Keep their verified local source and private candidate mapping; do not create a third visible message solely to retain that match. Keep other uncertain records under source-specific identities and visible review labels without inventing an Apple GUID or contact assignment. Apply short-code, blocked-sender, appointment-reminder, and whole-thread STOP/QUIT exclusions independently of other hold reasons. Repeated imports and missing source files must not remove retained rows or media. For owner-directed Apple deduplication, record the removed GUID and hash in `imessage_excluded_messages` before deleting a duplicate row, transfer any distinct source-attachment observations to the kept row, and keep media bytes.
- After paired import, catalog native attachment GUIDs from the same read-only source. Retain available files under archive-controlled media, including hidden opaque payloads; keep opaque assets out of ordinary media cards. Never treat a zero-message import as proof that all attachment bytes are present.
- Treat intermediate exporter output and Providers staging as replaceable input, never permanent storage. Preserve append-only retention when modifying exporter integration.
- Keep `README.md` installation/setup guidance and `docs/ARCHITECTURE.md` integration, version, and retention guidance accurate when changing this pipeline.
- Keep active Apple Messages/iCloud separate from the local historical archive. Do not write back to Apple's database or sync archive deletions to it.
- The optional `imessage-previews` command may read Apple's local database only in read-only mode to retain URL balloon images that TXT exports omit. Keep it explicit, scoped, fail-closed on ambiguous matches, and append-only; never rely on Apple-owned preview files as permanent storage.
- Reuse msgbrowse components and make minimal, targeted changes. Avoid new services, databases, frameworks, or dependencies without demonstrated need.
- Add regression tests for ingestion, storage, attachment, or retention changes, including repeated import and source deletion. Distinguish verified behavior from assumptions and do not claim archival safety without tests and real-history validation.
- Follow `~/.codex/AGENTS.md` for environment, test, type-check, and Git workspace rules. Direct user instructions take precedence.
